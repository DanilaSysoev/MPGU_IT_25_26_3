# Занятие №11: Поведенческие паттерны. Наблюдатель (Observer)

**Цель занятия:** Изучить паттерн Observer и событийную модель C# (`event`, `Action`). Научиться создавать системы, реагирующие на изменения состояния без жесткой связи между компонентами (Decoupling).

**Продолжительность:** 180 минут.

---

## Часть 1. Теория и Live Coding (90 минут)

### 1. Проблема жесткой связности (15 мин)

* **Контекст:** У нас есть Герой (`Hero`) и UI (`HealthBar`, `AchievementSystem`).
* **Плохое решение (Прямой вызов):**

    ```csharp
    class Hero {
        public void TakeDamage(int amount) {
            Health -= amount;
            HealthBar.Update(Health); // Жесткая связь! Герой знает про UI.
            AchievementSystem.Check("Survivor"); // Еще одна жесткая связь!
        }
    }
    ```

  * *Проблема:* Если мы захотим добавить "Звук удара", нам придется лезть в класс `Hero` и дописывать туда вызов `SoundManager`. Класс `Hero` превращается в помойку зависимостей.

### 2. Паттерн Observer (Классика) (25 мин)

* **Суть:** Один объект (Субъект/Publisher) ведет список зависимых объектов (Наблюдателей/Subscribers) и оповещает их об изменении своего состояния.
* **Метафора:** Подписка на YouTube-канал или газету.
  * Блогер (Publisher) выпускает видео.
  * Подписчики (Subscribers) получают уведомление. Блогер не знает их лично, ему всё равно, кто они.
* **UML:**
  * `ISubject`: Методы `Attach(IObserver)`, `Detach(IObserver)`, `Notify()`.
  * `IObserver`: Метод `Update(data)`.
  * `ConcreteSubject`: Хранит состояние и вызывает `Notify()`.
  * `ConcreteObserver`: Реализует реакцию на событие.

### 3. Observer в C# (Events & Delegates) (25 мин)

* В C# паттерн встроен в язык, поэтому интерфейсы `IObserver` писать не обязательно (хотя полезно для понимания).
* **Ключевые слова:** `event`, `delegate`, `Action`, `EventHandler`.
* **Синтаксис:**

    ```csharp
    public class Hero {
        // Объявление события (Action - делегат без возвращаемого значения)
        public event Action<int> OnHealthChanged;

        public void TakeDamage(int amount) {
            Health -= amount;
            // Оповещение подписчиков (если они есть)
            OnHealthChanged?.Invoke(Health); 
        }
    }
    ```

### 4. Live Coding: Система достижений (Achievments) (25 мин)

* **Задача:** Реализовать систему, которая выдает ачивку "Берсерк", если игрок убил 5 врагов.
* **Шаг 1. Субъект (Enemy):**

    ```csharp
    public class Enemy {
        // Статическое событие! (Любой враг умер)
        public static event Action<Enemy> OnEnemyDied;

        public void Die() {
            Console.WriteLine("Enemy Died");
            OnEnemyDied?.Invoke(this); // Кричим на весь мир
        }
    }
    ```

* **Шаг 2. Наблюдатель (AchievementSystem):**

    ```csharp
    public class AchievementSystem {
        private int _killCount = 0;

        public AchievementSystem() {
            // Подписка
            Enemy.OnEnemyDied += HandleEnemyDeath;
        }

        private void HandleEnemyDeath(Enemy enemy) {
            _killCount++;
            if (_killCount == 5) Console.WriteLine("ACHIEVEMENT UNLOCKED: BERSERK!");
        }
    }
    ```

* **Шаг 3. Важный момент (Memory Leak):**

  * Объяснить, что если мы подписались (`+=`), мы обязаны отписаться (`-=`), иначе объект не будет удален сборщиком мусора (GC). Это частая ошибка в Unity/C#.

## Часть 2. Практическое задание (Домашняя работа) (90 минут + дом)

**Тема:** Реактивная система событий.

### Задание (На выбор)

#### Вариант А: UI и HUD (Для всех)

1. **Создать событие:** В классе `Player` (или `GameManager`) создать событие `OnHealthChanged` (или `OnScoreChanged`).
2. **Создать подписчика:** Класс `ConsoleHUD` (или просто `UI`), который подписывается на это событие и выводит в консоль красивую строку состояния: `[HP: ||||||....] 60/100`.
3. **Демонстрация:** В основном цикле игры нанести урон игроку и убедиться, что UI обновился *автоматически*, без прямого вызова метода отрисовки из класса игрока.

#### Вариант Б: Система квестов/Достижений (Продвинутый)

1. **Создать событие:** В классе `Item` (или `Inventory`) событие `OnItemPickedUp`.

    * *Логика:* "Собери 3 яблока".
    * При поднятии предмета квест проверяет, яблоко ли это. Если да — увеличивает счетчик. Если собрано 3 — пишет "Квест выполнен!" и отписывается от событий.
3. **Демонстрация:** Симулировать подбор предметов и завершение квеста.
4. **Результат работы влейте в main с коммитом "Task 11 ready."**

## Критерии оценивания (Максимум 8 баллов)

| Критерий | Баллы | Описание |
| :--- | :---: | :--- |
| **Использование Events** | **2** | В коде использованы ключевые слова `event` и делегаты (`Action` / `EventHandler`). Событие объявлено в правильном месте (в Субъекте). |
| **Слабая связность** | **1** | Класс-источник события (`Player`) ничего не знает о классе-подписчике (`UI`). Нет ссылок на UI внутри Player. |
| **Подписка / Отписка** | **1** | Продемонстрирована корректная подписка (`+=`) и, желательно, отписка (`-=`) в методе `Dispose` или деструкторе (если применимо). |
| **Передача данных** | **1** | Событие передает полезную нагрузку (аргументы): `Invoke(currentHealth)`, а не просто пустой сигнал. |
| **Качество кода** | **1** | Понятные имена событий (`On...`), отсутствие логики в обработчиках (они должны только реагировать). Покрытие тестами |
| **Тесты** | **2** | Работа событий покрыта unit-тестами |
| **Итого** | **8** | |

### Штрафы

* **Прямой вызов:** `-3 балла`. Если вместо события студент просто вызывает метод `ui.Update()` внутри `Player`. Это нарушение сути паттерна.
* **Public Delegate:** `-1 балл`. Если событие объявлено как `public Action ...` без ключевого слова `event`. Это позволяет кому угодно "стереть" подписчиков (`= null`), нарушая инкапсуляцию.
* **Спам событиями:** `-1 балл`. Если событие вызывается в `Update` каждый кадр, даже если здоровье не изменилось. (Нужна проверка `if (value != _health)`).

### Методический комментарий

* **События vs Интерфейсы:** Студенты спросят: *"Зачем нам `event`, если можно сделать список `List<IObserver>`?"*.
  * *Ответ:* `event` — это синтаксический сахар над списком делегатов. Это удобнее, короче и безопаснее (никто снаружи не может вызвать `Invoke`, кроме самого класса). Но суть та же.
* **Static Events:** Предупредите их об опасности статических событий (`public static event`). Если на них подписываются обычные объекты, эти объекты *никогда* не удалятся из памяти до закрытия программы, если не отписаться вручную. Это классический Memory Leak. Для учебного проекта допустимо, но упомянуть стоит.
