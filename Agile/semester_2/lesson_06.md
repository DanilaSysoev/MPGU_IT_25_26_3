# Занятие №6: Unit-тестирование и качество кода

**Цель занятия:** Познакомить студентов с культурой автоматического тестирования, структурой теста (AAA), фреймворком xUnit (или NUnit) и научить писать тесты для *логики*, отделяя её от *представления*.

**Продолжительность:** 180 минут.

---

## Часть 1. Теория и Мотивация (45 минут)

### 1. Зачем нам тесты? (10 мин)

* **Проблема:** "Я поправил формулу урона у Орка, и теперь у меня Игрок перестал лечиться".
* **Регрессия:** Ситуация, когда новый код ломает старый. Руками проверять всё каждый раз — невозможно.
* **Unit-тест (Модульный тест):** Это маленький робот, который проверяет одну конкретную деталь (метод) вашего конструктора Lego.

### 2. Пирамида тестирования (кратко) (10 мин)

* Unit (Модульные) — много, быстрые, дешевые.
* Integration (Интеграционные) — проверяют связку (База + Код).
* E2E (UI) — проверяют, как пользователь кликает мышкой. Медленные, дорогие.
* *Мы фокусируемся на основании пирамиды (Unit).*

### 3. Структура теста AAA (15 мин)

* Любой тест состоит из трех фаз:
    1. **Arrange (Подготовка):** Создаем объекты, настраиваем данные.
    2. **Act (Действие):** Вызываем метод, который проверяем.
    3. **Assert (Проверка):** Сравниваем то, что получили, с тем, что ожидали.
* *Пример:*
  * Arrange: Есть герой со здоровьем 10.
  * Act: Герой получает 2 урона.
  * Assert: Здоровье должно стать 8.

### 4. Что тестировать? (10 мин)

* **Чистые функции:** `2 + 2 = 4`. Всегда. Это легко тестировать.
* **Войд-методы и UI:** `Console.WriteLine("Hello")`. Как проверить, что текст появился? Сложно.
* **Правило:** Мы тестируем **логику** (математику, состояние), а не **вывод** на экран. Если ваш метод смешивает логику и `Console.WriteLine` — его нужно рефакторить.

## Часть 2. Live Coding (Демонстрация) (90 минут)

**Инструментарий:** Visual Studio / Rider + **xUnit** (стандарт де-факто в .NET Core).

**Сценарий демонстрации:**

1. **Подготовка Solution (Самый важный технический момент):**
    * У нас есть проект `Game`.
    * Создаем **новый проект** в том же Solution: `Game.Tests` (тип: xUnit Test Project).
    * В проекте `Game.Tests` делаем **Add Project Reference** -> выбираем `Game`.
    * *Объясняем:* Тесты лежат отдельно, чтобы не попадать в финальную сборку игры.

2. **Пишем тестируемый класс (в проекте Game):**
    * Создаем класс `HealthComponent` (или `Calculator`).
    * Методы: `TakeDamage(int amount)`, `Heal(int amount)`, свойство `CurrentHealth`.
    * *Важно:* Никаких `Console.WriteLine` внутри! Только математика.

3. **Пишем первый тест (Positive Case):**

    ```csharp
    [Fact]
    public void TakeDamage_WithPositiveAmount_ShouldReduceHealth()
    {
        // Arrange
        var health = new HealthComponent(100); // 100 HP

        // Act
        health.TakeDamage(10);

        // Assert
        Assert.Equal(90, health.CurrentHealth);
    }
    ```

    * Запускаем Test Explorer. Видим зеленую галочку. Радуемся.

4. **Пишем тест на граничные условия (Edge Cases):**
    * *Вопрос:* Что будет, если урон больше здоровья?
    * *Тест:* `TakeDamage_MoreThanHealth_ShouldNotGoBelowZero`.
    * *Реализация:* Если HP стало -10, тест падает. Идем в код, добавляем `if (hp < 0) hp = 0;`. Тест проходит.
    * *Вопрос:* Что будет, если передать отрицательный урон? (Это лечение?). Добавляем проверку и выбрасываем исключение `ArgumentException`.
    * *Тест на исключение:* `Assert.Throws<ArgumentException>(() => health.TakeDamage(-5))`.

## Часть 3. Практическое задание (Домашняя работа) (45 минут + дом)

**Тема:** Покрытие логики проекта Unit-тестами.

### Задание

1. **Настройка окружения:**
    * Создать в своем решении (Solution) новый проект с именем `[YourGameName].Tests`.
    * Подключить библиотеку тестирования (xUnit или NUnit).
    * Добавить ссылку (Reference) на основной проект с игрой.
2. **Выбор цели:**
    * Найти в своем проекте класс, отвечающий за логику или расчеты.
    * *Идеальные кандидаты:* Система здоровья, Инвентарь (добавить/удалить предмет), Система опыта (Level Up), Боевая система (расчет урона с учетом брони).
    * *Плохие кандидаты:* `GameManager` (слишком сложный), Классы отрисовки карты.
3. **Написание тестов:**
    * Написать минимум **5 тест-кейсов** (Test Cases).
    * Среди них должен быть хотя бы один **Позитивный** сценарий (все работает штатно).
    * Среди них должен быть хотя бы один **Негативный/Граничный** сценарий (урон больше здоровья, попытка удалить несуществующий предмет, лечение мертвого персонажа).
4. **Рефакторинг (если нужно):**
    * Если ваш метод невозможно протестировать (он ничего не возвращает и не меняет публичных свойств, а только пишет в консоль) — **перепишите метод**. Отделите расчеты от вывода.

**Дедлайн:** 1 неделя.

## Критерии оценивания (Максимум 8 баллов)

| Критерий | Баллы | Описание |
| :--- | :---: | :--- |
| **Структура проекта** | **2** | Тесты находятся в отдельном проекте. Проект компилируется. Test Explorer видит тесты. |
| **Структура AAA** | **2** | В коде тестов явно выделены фазы Arrange, Act, Assert (комментариями или отступами). |
| **Покрытие (5 тестов)** | **2** | Написано минимум 5 осмысленных тестов для выбранной логики. |
| **Граничные случаи** | **1** | Есть проверка неочевидных ситуаций (0, отрицательные числа, null, переполнение). |
| **Качество кода** | **1** | Понятные имена тестов. Например: `Heal_DeadCharacter_ShouldNotResurrect`. |
| **Итого** | **8** | |

### Штрафы

* **Тестирование UI:** `-2 балла`. Если в тесте происходит перехват консольного вывода или попытка тестировать метод `Draw()`. Это не Unit-тест.
* **Отсутствие Assert:** `-2 балла`. Тест выполняется, но в конце нет проверки (`Assert...`). Такой тест всегда зеленый, но бесполезный.
* **Зависимость тестов:** `-1 балл`. Если Тест Б работает только после запуска Теста А (используют одну статическую переменную). Тесты должны быть изолированы.
* **Assert.True(true):** `-1 балл`. За фиктивные проверки ради количества.

### Методический комментарий

* **Проблема `internal` классов:** Студенты столкнутся с тем, что их классы в игре помечены как `internal` (по умолчанию в C#) или не имеют модификатора (тоже `internal`). Тестовый проект их не увидит.
  * *Решение 1:* Сделать классы `public`. (Просто и понятно).
  * *Решение 2:* Добавить `[assembly: InternalsVisibleTo("Game.Tests")]`. (Продвинуто, можно упомянуть как "Best Practice", но не требовать).
* **Именование тестов:** Настаивайте на длинных именах методов тестов. Имя теста — это единственная документация, которая не врет.
  * Плохо: `Test1`, `DamageTest`.
  * Хорошо: `TakeDamage_ArmorIsGreater_HealthShouldNotChange`.
* **Mocking:** Пока **не трогаем** Mock-объекты (Moq/NSubstitute). Это взорвет им мозг на 6-м занятии. Пусть тестируют то, что не имеет внешних зависимостей (State-based testing).
