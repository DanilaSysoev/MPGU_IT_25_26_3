# Занятие №15: Релиз, Документация и Полировка (Release Candidate)

**Цель занятия:** Подготовить проект к финальной защите. Научиться собирать (Build/Publish) приложение в автономный исполняемый файл, написать понятную документацию (README) и устранить критические баги.

**Продолжительность:** 180 минут.

Пятнадцатое занятие — **Подготовка к релизу**. Это не про программирование, это про **инженерию продукта**. Никто не будет играть в игру, которую невозможно запустить без Visual Studio. Никто не поймет, как в неё играть, если нет инструкции.

**Методическая цель:** Научить студентов упаковывать свой продукт, писать документацию и полировать UX (User Experience). Сделать из "лабораторной работы" **Продукт**.

---

## Часть 1. Теория и Воркшоп (90 минут)

### 1. Что такое Release? (15 мин)

* **Debug vs Release:**
  * *Debug:* Медленнее, содержит отладочную информацию (PDB), не оптимизирован.
  * *Release:* Быстрее, меньше весит, код оптимизирован компилятором.
* **Self-Contained Deployment (SCD):**
  * *Проблема:* "У меня на компьютере работает, а у друга нет .NET Runtime".
  * *Решение:* Упаковать рантайм .NET *вместе* с игрой в один EXE файл.
  * *Команда:* `dotnet publish -c Release -r win-x64 --self-contained -p:PublishSingleFile=true -p:UseAppHost=true`.

### 2. Документация (README.md) (30 мин)

* **Зачем?** Это лицо проекта на GitHub. Рекрутеры не будут качать код, они будут читать README.
* **Структура хорошего README:**
    1. **Название и Логотип (ASCII Art):** "Super RPG".
    2. **Описание:** О чем игра? (Жанр, Сюжет).
    3. **Скриншоты / GIF:** Как это выглядит? (Обязательно!).
    4. **Как запустить?** (Скачать -> Распаковать -> Запустить EXE).
    5. **Управление:** (WASD - ходить, Space - атака).
    6. **Архитектура:** Какие паттерны использованы (Factory, Strategy, Observer...) и *зачем*. (Это покажет вашу квалификацию).

### 3. Полировка UX (User Experience) (30 мин)

* **Проблема "Черного экрана":**
  * Игрок запускает консоль, а там пустота. Он думает, что игра зависла.
  * *Решение:* Вывести "Loading...", "Press Any Key to Start", "Welcome!".
* **Обработка ошибок:**
  * Если файл сохранения битый — игра не должна падать (`try-catch`). Она должна сказать: "Save corrupted, starting new game".
  * Если БД недоступна — "Server error, playing offline".

### 4. Воркшоп: Сборка релиза (15 мин)

* Все студенты прямо на паре пробуют собрать Release-версию своей игры в один файл.
* Запускают этот файл *вне* IDE (просто двойным кликом из папки).
* *Типичная проблема:* Не копируются ассеты (текстуры, звуки, конфиги).
  * *Решение:* Скопировать ассеты вручную.

## Часть 2. Практическое задание (Домашняя работа) (90 минут + дом)

**Тема:** Финализация проекта (Release Candidate).

### Задание (Обязательное)

1. **Сборка (Build):**
    * Собрать проект в конфигурации **Release**.
    * Опубликовать (Publish) как **Self-Contained** (автономное) приложение минимум для двух платформ - Windows и Linux.
    * Результат: папка `publish`, в которой лежит `MyGame.exe` (и, возможно, пара DLL/JSON).
    * Проверить, что игра запускается на *другом* компьютере (или в виртуалке/песочнице), где не установлена Visual Studio.
    * Создать на Github Release своего проекта, куда загрузить архивы со сборкой и ассетами

2. **Документация (Docs):**
    * Написать качественный `README.md` в корне репозитория (см. п. 2 в части 1).
    * Добавить раздел **"Архитектурные решения"**: перечислить 3-5 паттернов, которые вы внедрили, со ссылками на файлы кода. (Пример: "Фабрика врагов — см. `EnemyFactory.cs`").
    * Добавить инструкцию по управлению.

3. **Полировка (Polish):**
    * Убрать все отладочные `Console.WriteLine` ("TEST 1", "HERE").
    * Добавить красивое приветствие при старте и прощание при выходе.
    * Убедиться, что нет критических багов (Crash).

4. **Результат работы влейте в main с коммитом "Task 15 ready."**

**Дедлайн:** 1 неделя (К следующему занятию — Защите).

## Критерии оценивания (Максимум 8 баллов)

| Критерий | Баллы | Описание |
| :--- | :---: | :--- |
| **Сборка (Release)** | **2** | Предоставлен архив с рабочей сборкой (EXE). Игра запускается без установленной IDE. |
| **README: Описание** | **2** | Есть название, описание геймплея, инструкция по запуску и управлению. Оформление с заголовками и списками (Markdown). |
| **README: Архитектура** | **2** | Описаны примененные паттерны. Студент понимает, *зачем* он их использовал. |
| **Отсутствие багов** | **1** | Игра не падает при старте, при некорректном вводе (буквы вместо цифр) и при выходе. |
| **UX / Полировка** | **1** | Интерфейс дружелюбен (есть меню, подсказки, сообщения об ошибках понятные). |
| **Итого** | **8** | |

### Штрафы

* **Debug вместо Release:** `-2 балла`. Если прислан Debug-билд с кучей PDB файлов и зависимостью от SDK.
* **Пустой README:** `-3 балла`. Без документации проект считается несданным (как продукт).
* **Crash:** `-2 балла`. Если игра падает с необработанным исключением (`IndexOutOfRange`, `NullReference`) во время проверки преподавателем (happy path).

### Методический комментарий

* **Важность этого этапа:** Объясните студентам, что на работе они будут делать именно это: CI/CD, документация, релизы. Код — это только 30% работы. Остальное — инфраструктура.
* **Лайфхак:** Предложите им добавить в README бейдж (значок) "Build Passing" или "License: MIT". Это выглядит профессионально и мотивирует.
* **Git Releases:** Покажите вкладку "Releases" на GitHub. Пусть они зальют свой ZIP-архив туда и прикрепят ссылку в README. Это высший пилотаж для джуниора.
