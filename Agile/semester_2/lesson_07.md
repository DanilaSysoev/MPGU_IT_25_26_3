# Занятие №7: Паттерн Decorator (Декоратор)

**Цель занятия:** Изучить структурный паттерн Decorator. Научиться динамически добавлять объектам новые обязанности (функционал) без изменения их кода и без создания гигантской иерархии наследования.

**Продолжительность:** 180 минут.

---

## Часть 1. Теория и Live Coding (90 минут)

### 1. Проблема: "Взрыв наследования" (15 мин)

* **Контекст:** У нас в игре есть оружие.
  * Базовый класс `Weapon`.
  * Наследник `Sword` (урон 10).
  * Наследник `Axe` (урон 15).
* **Задача:** Мы хотим добавить механику "Зачарования". Меч может быть огненным (+5 урона) или ледяным (+3 урона).
* **Плохое решение (Наследование):**
  * Создаем `FireSword`, `IceSword`, `FireAxe`, `IceAxe`.
* **Усложнение:** А что, если меч может быть *одновременно* и огненным, и ледяным? И еще "Святым"?
  * Нам придется создавать класс `HolyFireIceSword`.
  * Если у нас 10 видов оружия и 10 видов зачарований — количество классов перевалит за сотню. Это называется **Combinatorial Explosion** (Комбинаторный взрыв).
* **Вывод:** Наследование — слишком жесткая связь. Нам нужен способ "надевать" новые свойства на объект динамически, как одежду на куклу.

### 2. Паттерн Decorator (Теория) (20 мин)

* **Аналогия:** Матрешка или "Обертка" (Wrapper).
  * В центре — Меч.
  * Мы кладем Меч в оболочку "Огонь". Снаружи эта конструкция все еще выглядит как Оружие (имеет метод `GetDamage`).
  * Мы кладем "Огненный Меч" в оболочку "Заточка".
* **UML схема (на доске):**
  * `IWeapon` (Интерфейс): Метод `GetDamage()`.
  * `Sword` (ConcreteComponent): Реализует `GetDamage() { return 10; }`.
  * `WeaponDecorator` (Base Decorator): Тоже реализует `IWeapon`! И хранит в себе ссылку на *другой* `IWeapon`.
  * `FireModifier` (Concrete Decorator): В методе `GetDamage()` вызывает базовый урон и прибавляет свой.

### 3. Live Coding: Система модификации оружия (55 мин)

*Преподаватель пишет код, студенты могут повторять.*

**Шаг 1. Создаем Интерфейс (Контракт):**
Самое важное — декоратор и декорируемый объект должны выглядеть одинаково для остальной программы.

```csharp
// Компонент
public interface IWeapon
{
    int GetDamage();
    string GetDescription();
}
```

**Шаг 2. Создаем Базовое оружие:**

```csharp
// Конкретный Компонент
public class Sword : IWeapon
{
    public int GetDamage() => 10;
    public string GetDescription() => "Простой меч";
}
```

**Шаг 3. Создаем Базовый Декоратор:**
Это "клей", который позволяет вкладывать объекты друг в друга.

```csharp
// Декоратор
public abstract class WeaponDecorator : IWeapon
{
    protected IWeapon _weapon; // Ссылка на оборачиваемый объект

    public WeaponDecorator(IWeapon weapon)
    {
        _weapon = weapon;
    }

    // По умолчанию просто пробрасываем вызовы дальше
    public virtual int GetDamage() => _weapon.GetDamage();
    public virtual string GetDescription() => _weapon.GetDescription();
}
```

**Шаг 4. Создаем Конкретные модификаторы:**
*Модификатор 1: Огненный урон (Прибавление)*

```csharp
public class FireDamage : WeaponDecorator
{
    public FireDamage(IWeapon weapon) : base(weapon) { }

    public override int GetDamage()
    {
        // Сначала берем базовый урон, потом добавляем свой
        return _weapon.GetDamage() + 5; 
    }

    public override string GetDescription()
    {
        return _weapon.GetDescription() + " + Огонь";
    }
}
```

*Модификатор 2: Критический удар (Умножение)*
*Здесь важно показать, что логика может быть сложнее сложения.*

```csharp
public class CriticalStrike : WeaponDecorator
{
    public CriticalStrike(IWeapon weapon) : base(weapon) { }

    public override int GetDamage()
    {
        // Умножаем весь накопленный урон на 2
        return _weapon.GetDamage() * 2; 
    }

    public override string GetDescription()
    {
        return "Критический " + _weapon.GetDescription();
    }
}
```

**Шаг 5. Клиентский код (Демонстрация):**
В `Main` или тесте показываем магию.

```csharp
void Main()
{
    // 1. Просто меч
    IWeapon mySword = new Sword();
    Console.WriteLine($"{mySword.GetDescription()} : {mySword.GetDamage()} урона"); 
    // Вывод: Простой меч : 10 урона

    // 2. Добавляем огонь
    mySword = new FireDamage(mySword);
    Console.WriteLine($"{mySword.GetDescription()} : {mySword.GetDamage()} урона");
    // Вывод: Простой меч + Огонь : 15 урона

    // 3. Добавляем крит (Обертываем уже огненный меч!)
    mySword = new CriticalStrike(mySword);
    Console.WriteLine($"{mySword.GetDescription()} : {mySword.GetDamage()} урона");
    // Вывод: Критический Простой меч + Огонь : 30 урона ( (10+5)*2 )
}
```

**Шаг 6. Важный нюанс (Порядок вызовов):**
*Вопрос к студентам:* "Что будет, если я сначала наложу Крит, а потом Огонь?"

* `CriticalStrike(Sword)` -> 10 * 2 = 20.
* `FireDamage(CritSword)` -> 20 + 5 = 25.
* *Результат:* 25 вместо 30.
* *Вывод:* Порядок декораторов имеет значение! В RPG это открывает простор для механик крафта ("Сначала точи, потом зачаровывай").

## Часть 2. Практическое задание (Домашняя работа) (90 минут + дом)

**Тема:** Система модификаторов (Stats/Abilities Modifier System).

### Задание

1. **Анализ проекта:**
    Найдите в своей игре сущность, характеристики которой могут временно или постоянно меняться под воздействием внешних факторов.
    * *Примеры:*
        * **RPG:** Оружие (урон), Броня (защита), Персонаж (характеристики: Сила, Ловкость).
        * **Гонки:** Машина (скорость, управляемость) — эффект "Нитро", "Пробитое колесо".
        * **Стратегия:** Юнит (атака, защита) — эффект "Аура командира", "Проклятие".
2. **Реализация Компонента (Component):**
    * Создайте интерфейс или абстрактный класс (например, `IMovable`, `IAttackable`, `IStatsProvider`) с методом получения значения (например, `GetSpeed()`, `GetDamage()`).
    * Создайте базовый класс (например, `BaseCar`, `BaseSword`), который возвращает "чистое" значение.
3. **Реализация Декораторов (Decorators):**
    * Создайте абстрактный декоратор, наследующий этот интерфейс.
    * Реализуйте минимум **два** конкретных декоратора, изменяющих возвращаемое значение.
        * *Пример:* `FireDamageDecorator` (+10 к урону), `RustDecorator` (ржавчина, -5 к урону, х0.8 к прочности).
4. **Интеграция:**
    * Продемонстрируйте создание цепочки декораторов в коде.
    * Покажите, что итоговое значение корректно рассчитывается (например, `Base(10) + Fire(5) + Rust(-2) = 13`).
5. **Тест (Bonus):**
    * Напишите Unit-тест, который проверяет правильность подсчета в цепочке из 3-х декораторов.
6. **Результат работы влейте в main с коммитом "Task 7 ready."**

**Дедлайн:** 1 неделя.

## Критерии оценивания (Максимум 8 баллов)

| Критерий | Баллы | Описание |
| :--- | :---: | :--- |
| **Выбор сущности** | **1** | Паттерн применен к месту (изменение характеристик/поведения), а не просто ради галочки. |
| **Базовая структура** | **2** | Есть общий интерфейс (`Component`) и базовый класс (`ConcreteComponent`). Декоратор тоже реализует этот интерфейс. |
| **Цепочка декораторов** | **2** | Реализована возможность вкладывать декораторы друг в друга (`new Dec(new Dec(obj))`). |
| **Логика модификации** | **1** | Декораторы реально меняют данные (складывают, умножают, подменяют строку), а не просто пробрасывают вызов. |
| **Чистота кода / Git** | **1** | Понятные имена (`class FireSwordDecorator` — хорошо, `class Decorator1` — плохо). Ветка, PR. |
| **Тест / Демонстрация** | **1** | Есть Unit-тест, подтверждающий, что `10 + 5 = 15`. |
| **Итого** | **8** | |

### Штрафы

* **Наследование вместо агрегации:** `-3 балла`. Если декоратор наследуется от *конкретного* класса, а не от интерфейса/абстракции, и не принимает объект в конструктор. Это не декоратор.
* **Нарушение LSP:** `-1 балл`. Если декоратор ломает поведение базового класса (например, выбрасывает исключение там, где база работала).
* **Хардкод:** `-1 балл`. Если значения (+10, -5) "зашиты" внутри декоратора без возможности настройки через конструктор.

### Методический комментарий

* **Сложность:** Студенты часто путают **Decorator** и **Chain of Responsibility** (Цепочка обязанностей).
  * *Разница:* Декоратор *расширяет* поведение (добавляет свое + вызывает оригинал). Цепочка *передает* запрос дальше (или обрабатывает и не передает).
* **Пример из жизни:** `Stream` в .NET (`System.IO`).
  * `FileStream` (База) -> читает байты.
  * `BufferedStream` (Декоратор) -> буферизирует чтение.
  * `GZipStream` (Декоратор) -> разжимает байты.
  * Мы пишем: `new GZipStream(new BufferedStream(new FileStream(...)))`. Это классический декоратор. Приведите этот пример, он очень нагляден.
