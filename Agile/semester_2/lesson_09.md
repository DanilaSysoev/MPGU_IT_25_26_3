# Занятие №9: Ретроспектива и Рефакторинг (Technical Debt Day)

**Цель занятия:** Остановить наращивание функционала, выявить "запахи кода" (Code Smells), научиться читать чужой код (Peer Review) и провести безопасный рефакторинг с использованием Unit-тестов.

**Продолжительность:** 180 минут.

---

## Часть 1. Теория: Запахи кода и Технический долг (60 минут)

### 1. Что такое Технический долг? (10 мин)

* **Аналогия:** Грязная посуда.
  * Можно не мыть посуду неделю (писать быстрый и грязный код), чтобы быстрее поесть.
  * Но через неделю на кухню невозможно зайти (добавить новую фичу), потому что везде грызуны и запах.
  * Сегодня мы моем посуду.

### 2. Code Smells (Запахи кода) — Топ-5 для новичков (20 мин)

* **Magic Numbers (Магические числа):**
  * *Плохо:* `if (health < 50) ...` (Что такое 50? Почему не 49?)
  * *Хорошо:* `const int CriticalHealthThreshold = 50;`
* **Duplicated Code (Дублирование / DRY):**
  * *Плохо:* Один и тот же кусок логики (например, расчет урона) скопирован в `Orc` и в `Elf`.
  * *Хорошо:* Вынести в общий метод в базовом классе или в Utility-класс.
* **Long Method (Длинный метод):**
  * *Правило:* Если метод не влезает на один экран (или больше 20-30 строк) — его нужно разбить.
  * *Техника:* Extract Method.
* **God Object (Божественный объект):**
  * Класс `GameManager` или `Player`, который делает ВСЁ (и логику, и ввод, и вывод).
  * *Решение:* Разбить на `PlayerInput`, `PlayerStats`, `PlayerRenderer`.
* **Comments-Deodorant (Комментарии-дезодорант):**
  * *Плохо:* `// Увеличиваем здоровье на 10` перед строкой `h += 10;`.
  * *Хорошо:* Назвать метод `Heal(10)`. Код должен читаться без комментариев.

### 3. Рефакторинг и IDE (15 мин)

* **Главное правило:** Не менять функционал! Рефакторинг меняет *структуру*, но не *поведение*.
* **Safety Net:** Перед рефакторингом запускаем тесты (Занятие 6). Если тестов нет — пишем тест, *потом* рефакторим.
* **Инструменты IDE:**
  * Демонстрация `Right Click -> Refactor -> Extract Method`.
  * Демонстрация `Rename` (F2 / Ctrl+R,R). Объяснить, почему нельзя просто переписывать имя переменной вручную (сломаются ссылки).

### 4. Code Review (Культура) (15 мин)

* Как критиковать, чтобы не обидеть?
  * Не "Твой код — г...", а "Я не понял, что делает эта переменная `x`".
  * Не "Ты ошибся", а "Здесь может возникнуть NullReference".
  * Принцип бутерброда: Похвалить -> Поругать -> Похвалить.

## Часть 2. Peer Review (Взаимная проверка) (60 минут)

**Формат:** Студенты разбиваются на пары (желательно, чтобы сильный сидел со слабым, или рандомно).

**Задача:**

1. Обменяться ссылками на репозитории.
2. Выкачать (clone) проект партнера.
3. Попытаться запустить. (Если не запустилось — сразу **Issue** "Не работает из коробки").
4. Провести аудит кода по чеклисту (см. ниже).
5. Создать в репозитории партнера **Issue** (или файл `REVIEW.md`), где перечислить 3-5 найденных проблем ("запахов").

**Чеклист для ревью:**

* [ ] Есть ли "магические числа"?
* [ ] Есть ли методы длиннее 30 строк?
* [ ] Понятны ли названия переменных (`a`, `b`, `tmp` — плохо)?
* [ ] Есть ли закомментированные куски кода (мертвый код)?
* [ ] Используются ли паттерны (Singleton, Factory) там, где они заявлены?
* [ ] Лежат ли файлы по папкам или всё в куче?

*Преподаватель ходит между рядами, модерирует споры и подсказывает, является ли код "запахом" или нет.*

## Часть 3. Практическое задание (Домашняя работа) (60 минут + дом)

**Тема:** Большой Рефакторинг (The Big Clean-up).

### Легенда

Заказчик (преподаватель) заморозил разработку новых фич. Пришел отчет от отдела QA и аудиторов (вашего партнера по парте). Нужно устранить замечания, иначе проект станет неподдерживаемым.

### Задание

1. **Анализ Issue:** Прочитать замечания, которые оставил партнер (или преподаватель).
2. **Создание ветки:** `fix/refactoring-week9`.
3. **Исправление запахов (минимум 3):**
    * **Extract Method:** Найти самый длинный метод в проекте и разбить его на 3-4 маленьких метода с понятными именами.
    * **Rename:** Переименовать непонятные переменные/методы (`DoIt` -> `CalculateDamage`).
    * **Magic Constants:** Заменить числа на именованные константы (`const int MaxInventorySize = 10`).
    * **Dead Code:** Удалить весь закомментированный код.
4. **Устранение God Object (для сильных):**
    * Если у вас есть класс на 300+ строк, вынести часть логики в вспомогательный класс (например, `ConsoleRenderer` вынести из `Game`).
5. **Документация:**
    * Обновить `README.md`: добавить раздел "Архитектура", перечислить, какие паттерны применены и где (в каких классах).
6. **Результат работы влейте в main с коммитом "Task 9 ready."**

**Дедлайн:** 1 неделя.

## Критерии оценивания (Максимум 8 баллов)

| Критерий | Баллы | Описание |
| :--- | :---: | :--- |
| **Peer Review (Участие)** | **2** | Студент провел ревью чужого проекта и оставил осмысленный отзыв (Issue/File) с минимум 3 замечаниями. |
| **Рефакторинг: Методы** | **2** | В коде (ветка `fix`) видно применение `Extract Method`. Длинные "простыни" кода разбиты на логические блоки. |
| **Рефакторинг: Имена** | **1** | Устранены имена `var1`, `temp`, `list`. Введены константы вместо магических чисел. |
| **Чистота** | **1** | Удален закомментированный мусор и неиспользуемые `using`. |
| **README / Docs** | **1** | Обновлено описание проекта, есть список используемых паттернов. |
| **Работоспособность** | **1** | После рефакторинга игра запускается и работает так же, как раньше (Regression testing). |
| **Итого** | **8** | |

### Штрафы

* **Сломанный билд:** `-4 балла`. Если после "улучшений" игра перестала компилироваться или падает при запуске. Главное правило рефакторинга нарушено.
* **Игнорирование замечаний:** `-2 балла`. Если партнер указал на явную ошибку (например, пароль в коде или абсолютный путь к файлу), а студент это не исправил.
* **Refactoring == Rewriting:** `-1 балл`. Если студент удалил всё и написал новую игру с нуля. Задача была именно *улучшить структуру существующего кода*.

### Методический комментарий

* **Психологический момент:** Студентам обидно, когда их код ругают.
  * *Ваша роль:* Объясните, что код — это не они сами. "Мы критикуем артефакт, а не человека". Code Review — это лучший способ учиться.
* **Git:** Обратите внимание, что рефакторинг часто вызывает **Merge Conflicts**, если студент параллельно что-то делал в другой ветке. Это хороший момент напомнить про Git Flow: "Сначала сливаем изменения, потом рефакторим, или наоборот, но не одновременно".
* **Оценка:** Если студенту не досталось пары (нечетное количество), ревью проводит преподаватель (вы), либо он делает ревью вашего примера кода с намеренно внесенными ошибками.
