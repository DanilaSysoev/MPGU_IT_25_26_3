## 1. Конспект занятия (План для преподавателя)

### Часть 1. Теория: Почему `print()` — это зло (30 мин)

*Цель: Объяснить разницу между stdout и structured logging.*

**Тезисы:**

1. **Print:**
    * Блокирует поток (в Python это медленно).
    * Нет меток времени.
    * Нет уровней важности (всё одинаково важно).
    * Нельзя перенаправить в файл/Graylog/Sentry без костылей.
2. **Levels (Уровни):**
    * `DEBUG`: "Я зашел в функцию X с аргументами Y". (Для разработки).
    * `INFO`: "Пользователь Z успешно вошел". (Бизнес-события).
    * `WARNING`: "Место на диске заканчивается" или "Подозрительная активность". (Надо глянуть, но пока работаем).
    * `ERROR`: "Не удалось сохранить файл". (Функция упала, но сервис жив).
    * `CRITICAL`: "БД недоступна". (Всё пропало).
3. **JSON Logs:** В продакшене логи должны быть машиночитаемыми (JSON), чтобы их могли парсить ELK/Splunk.

### Часть 2. Настройка `logging` в Python (40 мин)

*Цель: Заменить все принты на логгер.*

**Практика:**

1. Создаем `logger_config.py`.
2. Настраиваем форматтер: `%(asctime)s - %(name)s - %(levelname)s - %(message)s`.
3. Выводим в консоль (StreamHandler) и в файл (FileHandler).
4. **Секреты:** Осторожно! Не логируйте пароли и PII (персональные данные).

```python
import logging
import sys

# Создаем логгер
logger = logging.getLogger("file_manager")
logger.setLevel(logging.INFO)

# Форматтер
formatter = logging.Formatter('%(asctime)s - %(levelname)s - %(message)s')

# Хендлер (вывод в консоль)
console_handler = logging.StreamHandler(sys.stdout)
console_handler.setFormatter(formatter)
logger.addHandler(console_handler)

# Хендлер (вывод в файл)
file_handler = logging.FileHandler("app.log")
file_handler.setFormatter(formatter)
logger.addHandler(file_handler)
```

### Часть 3. Обработка исключений (Exception Handling) (40 мин)

*Цель: Скрыть "кишки" приложения.*

**Тезисы:**

1. **FastAPI Default:** Если не обработать исключение, uvicorn вернет `500 Internal Server Error` и напечатает стектрейс в консоль (а иногда и юзеру, если `debug=True`).
2. **Middleware:** Глобальный перехватчик ошибок.
3. **Кастомные исключения:**
    * `HTTPException(404, "File not found")` — это хорошо.
    * `1 / 0` (ZeroDivisionError) -> `500` -> "Что-то пошло не так. ID ошибки: 12345".

**Практика:**

* Пишем глобальный обработчик `exception_handler` в `main.py`.
* Он ловит `Exception`.
* Логирует **полный стектрейс** (`logger.error(..., exc_info=True)`).
* Возвращает пользователю **красивый JSON**: `{"detail": "Internal Server Error", "request_id": "..."}`.

### Часть 4. Security Audit Logging (50 мин)

*Цель: Записывать "Кто, Что, Когда".*

**Тезисы:**

1. Обычные логи: "Приложение работает".
2. Аудит безопасности: "Пользователь Alice (IP: 1.2.3.4) попыталась скачать файл Bob (ID: 5) и получила 403".
3. Это нужно для расследований инцидентов (Forensics).

**Практика:**

* Добавляем логирование в Middleware (или Dependency) аутентификации.
* Логируем успешный вход, неудачный вход (важно для Fail2Ban), доступ к чужим файлам (IDOR попытки).

### Часть 5. Интеграция с Docker (20 мин)

*Цель: Чтобы логи не пропадали.*

**Тезисы:**

* Контейнер пишет в `stdout`. Docker ловит это.
* Команда `docker logs my-app` показывает всё.
* Если мы пишем в файл внутри контейнера (`app.log`), он должен лежать на **volume**, иначе пропадет при перезапуске!
* В `docker-compose.yml` добавляем volume для логов: `./logs:/app/logs`.

## 2. Домашнее задание №13: «Черный ящик»

**Легенда:**
Ваш сервис работает, но вы слепы. Вчера пользователи жаловались на "какую-то ошибку", а вы не знаете, в чем дело. А позавчера кто-то пытался подобрать пароль админа.
Вам нужно внедрить систему логирования, чтобы видеть всё, что происходит, и скрывать технические детали ошибок от посторонних глаз.

**Задание:**

1. **Настройка Логгера:**
    * Замените все `print()` в вашем коде на `logger.info()` / `logger.warning()`.
    * Настройте вывод логов в файл `logs/app.log` (не забудьте создать папку!).
    * Формат лога должен содержать время, уровень и сообщение.

2. **Глобальный обработчик ошибок (Middleware):**
    * Напишите функцию-обработчик для `Exception` (всех необработанных ошибок).
    * В случае ошибки (например, деление на ноль или падение БД):
        * Запишите полный текст ошибки (Traceback) в **лог-файл** (уровень ERROR).
        * Верните пользователю JSON с кодом 500 и текстом: `{"detail": "We are sorry, something went wrong."}`. **Никаких путей к файлам!**
    * Сделайте специальный тестовый эндпоинт `/cause_error`, который вызывает ошибку (например, `1/0`), чтобы проверить работу.

3. **Аудит безопасности:**
    * Добавьте логирование событий безопасности (уровень WARNING):
        * Неудачная попытка входа (неверный пароль).
        * Попытка доступа к чужому файлу (403/404 в IDOR).
    * В логе должно быть видно имя пользователя (если есть) и действие.

4. **Деплой и Volume:**
    * Обновите `docker-compose.yml`: добавьте volume `./logs:/app/logs`.
    * Деплойте на сервер.
    * Зайдите на сервер, вызовите ошибку (через `/cause_error`) и попробуйте войти с неправильным паролем.
    * Проверьте файл `logs/app.log` на сервере. Там должны быть записи.

**Формат сдачи:**

1. Ссылка на репозиторий.
2. Отчет (`report_13.md`):
    * Скриншот ответа сервера на `/cause_error` (красивый JSON, без стектрейса).
    * Скриншот файла `logs/app.log` с сервера, где виден ваш Traceback ошибки и запись о неудачном входе.
    * Скриншот `docker-compose.yml` с подключенным volume для логов.
3. **Результат работы влейте в main с коммитом "Task 13 ready."**
