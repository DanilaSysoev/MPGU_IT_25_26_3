## 1. Конспект занятия (План для преподавателя)

### Часть 1. Теория: "У меня на машине работает" (30 мин)

*Цель: Объяснить проблему зависимостей.*

**Тезисы:**

1. **Проблема:** Вы написали код на Ubuntu 22.04 с Python 3.10. Заказчик запускает на CentOS 7 с Python 3.6. Ничего не работает.
2. **Решение (Контейнер):** Это "легковесная виртуалка". В ней лежит ваша ОС (усеченная), ваши библиотеки и ваш код.
3. **Image vs Container:**
    * *Image (Образ):* Это чертеж здания (класс в ООП). Read-only.
    * *Container (Контейнер):* Это построенное здание (объект в ООП). В нем можно жить и писать файлы.
4. **Isolation (Изоляция):** Процессы в контейнере не видят процессов хоста. Файловая система своя. Сеть своя.

### Часть 2. Пишем Dockerfile (40 мин)

*Цель: Создать рецепт сборки нашего приложения.*

**Практика:**
Создаем файл `Dockerfile` в корне проекта:

```dockerfile
# 1. Базовый образ (на чем строим)
FROM python:3.10-slim

# 2. Рабочая директория внутри контейнера
WORKDIR /app

# 3. Копируем зависимости (requirements.txt)
COPY requirements.txt .

# 4. Устанавливаем зависимости
RUN pip install --no-cache-dir -r requirements.txt

# 5. Копируем исходный код
COPY . .

# 6. Команда запуска
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### Часть 3. Сборка и Запуск (Build & Run) (40 мин)

*Цель: Превратить рецепт в работающее приложение.*

**Команды:**

1. **Build:** `docker build -t file-manager:v1 .` (точка в конце важна!).
2. **Run:** `docker run -d -p 8000:8000 --name my-app file-manager:v1`.
    * `-d`: Detached (фоновый режим).
    * `-p 8000:8000`: Проброс порта (Host:Container).
3. **Logs:** `docker logs my-app`.
4. **Exec:** `docker exec -it my-app /bin/bash` (зайти внутрь контейнера).

**Демонстрация:**
Заходим на `localhost:8000/docs`. Работает!
Останавливаем: `docker stop my-app`. Удаляем: `docker rm my-app`.

### Часть 4. Docker Compose: Оркестрация (40 мин)

*Цель: Запускать приложение одной командой, а не простыней флагов.*

**Тезисы:**

1. В реальном проекте у вас будет App + DB + Redis + Nginx. Запускать их руками через `docker run` — ад.
2. **docker-compose.yml:** Файл-инструкция, где описаны все сервисы.

**Практика:**
Создаем `docker-compose.yml`:

```yaml
version: '3.8'

services:
  app:
    build: .
    ports:
      - "8000:8000"
    volumes:
      - ./storage:/app/storage  # Важно: Персистентность данных!
    env_file:
      - .env  # Пробрасываем секреты
```

Запускаем: `docker-compose up -d`.

### Часть 5. Деплой на сервер с Docker (30 мин)

*Цель: Показать магию переносимости.*

**Алгоритм:**

1. Устанавливаем Docker на сервере (если еще нет).
2. Клонируем репо.
3. Создаем `.env` (он в `.gitignore`, помните?).
4. `docker-compose up -d --build`.
5. Всё! Никаких `pip install`, `virtualenv` и конфликтов версий python на сервере.

## 2. Домашнее задание №11: «Упаковка и отправка»

**Легенда:**
Ваша команда переходит на микросервисную архитектуру. Руководство требует, чтобы ваше приложение запускалось на любом сервере одной командой, без ручной установки Python и библиотек. Кроме того, данные пользователей (файлы в папке `storage`) должны сохраняться даже при удалении контейнера.

**Задание:**

1. **Контейнеризация (Dockerfile):**
    * Напишите `Dockerfile` для вашего приложения.
    * Используйте легкий базовый образ (`python:3.10-slim` или `alpine`, если умеете).
    * Настройте копирование кода и установку зависимостей.

2. **Оркестрация (Docker Compose):**
    * Напишите `docker-compose.yml`.
    * Опишите сервис `app`.
    * **Volume (Важно):** Настройте volume для папки `storage`, чтобы файлы сохранялись на хост-машине (например, `./storage:/app/storage`). Если этого не сделать, при перезапуске контейнера все файлы исчезнут!
    * **Env File:** Подключите файл `.env`.

3. **Локальный тест:**
    * Соберите и запустите: `docker-compose up --build`.
    * Загрузите файл через Swagger.
    * Остановите контейнер (`Ctrl+C` или `docker-compose down`).
    * Запустите снова.
    * Проверьте, что загруженный файл никуда не делся (благодаря volume).

4. **Деплой на сервер (Обязательно):**
    * Закоммитьте `Dockerfile` и `docker-compose.yml`.
    * Зайдите на сервер по SSH.
    * Сделайте `git pull`.
    * Убедитесь, что на сервере есть файл `.env` с секретами.
    * Запустите приложение: `docker-compose up -d --build`.
    * Проверьте статус: `docker-compose ps`.

**Формат сдачи:**

1. Ссылка на репозиторий (с новыми файлами Docker).
2. Отчет (`report_11.md`):
    * Скриншот команды `docker-compose ps` на **сервере** (статус Up).
    * Скриншот содержимого папки `storage` на **сервере** (вне контейнера), подтверждающий работу volume (файлы появляются на хосте).
3. **Результат работы влейте в main с коммитом "Task 11 ready."**

## 3. Критерии оценивания (Максимум 8 баллов)

| Критерий | Баллы | Описание |
| :--- | :---: | :--- |
| **Dockerfile** | **2** | Файл написан корректно, билд проходит без ошибок. Используется `.dockerignore` (желательно, но не обязательно, + в карму). |
| **Docker Compose** | **2** | Файл `docker-compose.yml` корректен, сервис поднимается, порт проброшен. |
| **Volume (Persistance)** | **2** | Данные сохраняются при перезапуске контейнера. Это критически важно для файлового хранилища. |
| **Деплой на сервер** | **2** | Приложение успешно запущено на удаленном сервере в контейнере. |
| **Итого** | **8** | |

### Штрафы

* **-2 балла:** Контейнер падает при старте (например, не нашел `.env` или `requirements.txt`).
* **-2 балла:** Данные теряются при удалении контейнера (нет volume).
* **-1 балл:** Образ весит > 1ГБ (использован `FROM python:3.10` вместо `slim` или не почищен кэш apt/pip), хотя для учебного проекта это простительно.
