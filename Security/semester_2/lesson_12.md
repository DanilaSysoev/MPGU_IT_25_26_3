## 1. Конспект занятия (План для преподавателя)

### Часть 1. Проблема Root в контейнере (30 мин)

*Цель: Показать, что по умолчанию Docker небезопасен.*

**Демонстрация:**

1. Запускаем контейнер из прошлого урока: `docker-compose up -d`.
2. Заходим внутрь: `docker exec -it <container_id> bash`.
3. Пишем `whoami`. Ответ: `root`.
4. Пишем `id`. UID=0.
5. **Почему это плохо:** Если уязвимость позволяет "сбежать" из контейнера (Container Breakout), хакер сразу получает root на хост-машине. Принцип наименьших привилегий нарушен.

### Часть 2. Создание непривилегированного пользователя (50 мин)

*Цель: Переписать Dockerfile так, чтобы приложение работало от обычного юзера.*

**Практика (Рефакторинг Dockerfile):**
Мы используем образ `python:3.10-slim` (Debian).

1. **Создаем группу и юзера:**

    ```dockerfile
    # ... (установка зависимостей) ...

    # Создаем пользователя 'appuser' с UID 1000
    # --system: системный (без пароля)
    # --group: создать одноименную группу
    RUN addgroup --system appuser && adduser --system --group appuser
    ```

2. **Настройка прав (Permissions):**
    * Важный момент: `appuser` не может писать в папки, созданные root'ом.
    * Нужно передать права на рабочую директорию:

    ```dockerfile
    WORKDIR /app
    COPY . .
    # Меняем владельца всех файлов на нашего юзера
    RUN chown -R appuser:appuser /app
    ```

3. **Переключение:**

    ```dockerfile
    # С этого момента все команды выполняются от имени appuser
    USER appuser
    
    CMD ["uvicorn", "main:app", ...]
    ```

**Проблема с Volume (Важный нюанс):**
При монтировании папки `storage` с хоста, у неё могут быть права хостового пользователя. Если UID внутри (1000) и снаружи совпадают — всё ок. Если нет — будут ошибки `Permission denied`.
*Решение для урока:* На хост-машине (Linux) сделать `chmod 777 storage` (грубо, но работает для обучения) или `chown 1000:1000 storage`.

### Часть 3. Файл .dockerignore (20 мин)

*Цель: Не тащить секреты в образ.*

**Тезисы:**

1. Команда `COPY . .` копирует ВСЁ.
2. Если вы случайно скопировали `.env` в образ, а потом удалили его `RUN rm .env`, он **все равно останется в слоях** образа. Хакер может его достать.
3. `.dockerignore` работает как `.gitignore`.

**Практика:**
Создаем файл `.dockerignore`:

```text
.git
.env
venv
__pycache__
*.pyc
tests/
Dockerfile
docker-compose.yml
```

### Часть 4. Сканирование образов (Trivy) (50 мин)

*Цель: Найти CVE в системных библиотеках.*

**Инструмент:** **Trivy** (от Aqua Security) — самый популярный сканер.
Мы не будем ставить его локально (сложно для новичков), мы запустим его... **в докере**!

**Команда:**

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
    aquasec/trivy image file-manager:v1
```

*(Объясняем: мы даем триви доступ к демону докера, чтобы он мог прочитать наши образы).*

**Анализ отчета:**

* **CRITICAL / HIGH:** Надо чинить. Часто лечится обновлением базового образа (например, `python:3.10.13-slim` вместо просто `3.10-slim`).
* **LOW:** Можно игнорировать в рамках учебного курса.

### Часть 5. Минимизация образа (30 мин)

*Цель: Удалить лишнее.*

**Тезисы:**

* Чем меньше образ, тем меньше поверхность атаки.
* Не оставляйте кэш apt/pip.
* Пример чистки в одной команде:

    ```dockerfile
    RUN pip install -r requirements.txt \
        && rm -rf /root/.cache/pip
    ```

## 2. Домашнее задание №12: «Броня для контейнера»

**Легенда:**
Аудит безопасности показал, что ваше приложение запускается от `root`. Это недопустимый риск. Кроме того, в образе найдены уязвимые системные библиотеки.
Вам нужно "закалить" (harden) ваш Docker-образ.

**Задание:**

1. **Non-root User:**
    * Модифицируйте `Dockerfile`.
    * Создайте пользователя `appuser`.
    * Назначьте ему права на папку `/app`.
    * Переключите контекст исполнения (`USER appuser`).
    * *Проверка:* Зайдите в запущенный контейнер (`docker exec ... bash`) и введите `whoami`. Должно быть `appuser`.

2. **Dockerignore:**
    * Создайте `.dockerignore`.
    * Убедитесь, что папка `.git`, файл `.env` и виртуальное окружение `venv` не попадают в контекст сборки (размер образа должен немного уменьшиться).

3. **Сканирование (Trivy):**
    * Соберите образ.
    * Просканируйте его с помощью Trivy (или Docker Scout, если используете Docker Desktop: `docker scout quickview`).
    * Сохраните отчет (скриншот или текстовый файл).
    * Попробуйте обновить базовый образ до более свежей версии (patch version), если есть критические уязвимости.

4. **Деплой и Права доступа (Linux Server):**
    * Запушьте изменения.
    * Обновитесь на сервере (`git pull`).
    * Пересоберите контейнеры (`docker-compose up -d --build`).
    * **Важный момент:** Скорее всего, приложение упадет с ошибкой `Permission denied` при попытке загрузить файл, так как папка `storage` на сервере принадлежит `root`, а внутри контейнера теперь `appuser`.
    * **Исправьте это:** На сервере выполните `chown -R 1000:1000 storage` (или `chmod 777 storage`, если ленитесь, но лучше chown).
    * Проверьте, что загрузка файлов снова работает.

**Формат сдачи:**

1. Ссылка на репозиторий (обновленный Dockerfile, .dockerignore).
2. Отчет (`report_12.md`):
    * Скриншот команды `whoami` внутри контейнера (результат: не root).
    * Скриншот отчета сканера Trivy.
    * Скриншот работающей загрузки файлов на сервере (подтверждение, что права доступа настроены верно).
3. **Результат работы влейте в main с коммитом "Task 12 ready."**
